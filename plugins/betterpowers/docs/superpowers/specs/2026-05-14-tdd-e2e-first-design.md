# TDD 流程优化设计：默认采用大粒度 E2E First

**日期：** 2026-05-14  
**状态：** Draft

## 问题

当前 `test-driven-development` 技能将 TDD 强绑定为“小粒度测试先行”的默认开发方式。对于 superpowers 这类以技能、工作流、代理行为约束为核心的仓库，这种默认方式会带来三个问题：

1. **流程过碎**：代理容易过早拆到函数级、模块级测试，迟迟不能验证真实功能路径是否成立。
2. **阻塞与循环偏多**：在实现主流程前，代理会频繁陷入“补更多小测试 → 改一点实现 → 再补测试”的局部循环，影响整体推进。
3. **与真实验收目标错位**：很多改动最终是为了保证一个完整工作流、技能触发链路或用户可见行为成立，但当前 TDD 默认从局部单测起步，容易把注意力放在局部实现而非端到端结果。

用户希望将默认 TDD 主流程调整为：**仍然坚持 test-first，但第一条失败测试默认改为带相对复杂输入的 E2E 测试**。只有当大粒度测试失败，或者暴露出性能/稳定性类异常时，才回退到更小粒度的模块测试或单元测试进行定位和修复。

## 目标

1. 保留 TDD 的核心原则：**先写测试，再写实现**。
2. 将 `test-driven-development` 的默认起手式改为：**复杂输入的 E2E failing test first**。
3. 将“小粒度测试”从默认入口调整为**失败后的定位工具**，而非所有任务的默认起点。
4. 减少代理在实现前期的碎片化阻塞和过早下钻。
5. 让技能更贴近 superpowers 仓库常见任务：技能行为、流程编排、触发链路、跨文件工作流。

## 非目标

1. 不是取消 TDD，也不是允许“先写实现、后补测试”。
2. 不是要求所有任务永远只写 E2E，而是将其设为默认入口。
3. 不是完全废除小粒度测试；它们仍用于故障定位、边界验证和自然无法做 E2E 的任务。
4. 本设计不直接修改 `brainstorming`、`verification-before-completion`、`subagent-driven-development` 的主流程，只在需要处更新它们与 TDD 的衔接描述。
5. 本设计不定义具体框架测试命令（如 Playwright、Vitest、Jest、Go test）；技能只定义方法，不绑定工具链。

## 设计原则

### 1. 先验证真实功能路径，再验证局部正确性

默认优先回答“用户主流程是否成立”，而不是先回答“某个局部函数是否正确”。

### 2. 大粒度优先，但必须保持 test-first

新的默认流程不是“先实现再跑 E2E”，而是“先写一个会失败的 E2E/集成级测试，再实现到通过”。这保留了 TDD 的核心约束。

### 3. 小粒度测试是诊断手段，不是默认仪式

模块测试/单元测试仍然重要，但默认只在以下情况介入：
- E2E/集成测试失败，且原因不清楚
- 暴露出性能、稳定性、时序、flaky 等异常
- 任务天然不适合从 E2E 起步

### 4. 第一条测试必须使用相对复杂输入

大粒度测试不能只覆盖最简单 happy path。默认要求选择**能代表真实使用复杂度的输入**，以便更早暴露流程级问题、边界问题和集成问题。

### 5. 例外必须明确，而不是让代理自由发挥

只有当任务天然无法成立 E2E/流程级测试时，才允许回退到小粒度测试起步，例如：纯工具函数、纯解析逻辑、没有独立主流程可跑的底层模块修改。

## 总体设计

### 1. 重写 `test-driven-development` 的主叙事

当前技能的核心口径是：
- 写一个最小失败测试
- 通常以小粒度行为为单位
- 每个新函数/方法都要先有测试

重写后，技能的核心口径改为：

> 默认先写一个带复杂输入的 E2E 或集成级失败测试，先证明完整功能路径应该成立；只有当该测试失败且无法直接定位，或出现稳定性/性能异常时，再向下拆到模块级或单元级测试定位问题。

这样做的关键变化不是否定 TDD，而是重新定义 **“第一条失败测试应该站在哪个层级”**。

### 2. 将 TDD 主流程改为“两层漏斗”

新的默认流程分成两层：

#### 第一层：大粒度实现漏斗（默认入口）

1. 先定义要成立的完整行为
2. 编写一条 E2E 或集成级失败测试
3. 该测试使用相对复杂、接近真实使用的输入
4. 运行测试，确认它因“功能尚未实现/行为不符合预期”而失败
5. 实现主流程，直到该大粒度测试通过

这一层的目标是：**先把功能做通，而不是先把内部结构切细。**

#### 第二层：小粒度诊断漏斗（失败后进入）

仅在以下情况进入：
- 大粒度测试失败，但失败原因不直接清晰
- 测试结果不稳定，出现 flaky/时序问题
- 出现性能或资源异常，无法仅靠 E2E 结果定位

进入后：
1. 针对可疑模块补写更小粒度的失败测试
2. 用这些测试定位问题核心
3. 修复实现
4. 回到大粒度测试重新验证主流程

这一层的目标是：**用小测试找根因，而不是默认把整个开发过程拆成小测试。**

### 3. 明确“复杂输入”的含义

技能不应只说“写 E2E”，而应明确第一条测试的输入要求。所谓“相对复杂输入”，指的是：

- 比最小 happy path 更接近真实业务路径
- 包含足以穿透多个判断/阶段/步骤的数据
- 能覆盖真实使用中常见的上下文组合
- 足以让代理较早发现流程集成问题，而不是只验证表面可运行

技能不应把“复杂输入”硬编码成某一类数据规模，而应将其定义为：**优先选择能代表真实使用复杂度、能跨越多个内部边界的输入**。

### 4. 定义何时允许补小粒度测试

技能需要把“什么时候下钻”写成硬条件，避免代理重新滑回旧习惯。允许进入小粒度验证的触发条件只有三类：

1. **大粒度测试失败**，且无法直接从失败信息定位问题
2. **出现稳定性异常**，如 flaky、时序依赖、偶发失败、重复跑结果不一致
3. **出现性能/资源异常**，如明显超时、资源占用异常、关键路径退化，需要局部定位

如果只是“感觉写几个单测更保险”“先把函数测一遍比较顺手”，不构成允许下钻的理由。

### 5. 定义不适合 E2E 的例外路径

对天然不适合从 E2E 起步的任务，技能应提供明确例外，而不是逼代理生造大测试。例外包括：

- 纯工具函数
- 纯解析/转换逻辑
- 没有独立主流程可运行的底层模块修改
- 明显只能通过局部输入输出定义行为的原子逻辑

这些任务允许直接从模块测试/单元测试起步，但仍必须满足 test-first：先写失败测试，再写实现。

## 对技能文本的具体改动方向

### 1. Frontmatter

当前描述：

> Use when implementing any feature or bugfix, before writing implementation code

建议保持触发条件不变，不在 description 里提前剧透完整流程，但正文应重写为“大粒度优先”的 TDD 版本。description 可以只轻微增强为：

> Use when implementing any feature or bugfix, before writing implementation code; defaults to end-to-end or integration failing tests before smaller-scope diagnosis

如果担心 description 过度总结流程导致代理只读 frontmatter，也可以保留当前 description，不做改动。

### 2. Overview

Overview 需要从“write the test first”扩展为：

- 默认先写 **大粒度失败测试**
- 第一条测试优先覆盖 **完整行为路径**
- 小粒度测试在失败定位阶段再引入

### 3. When to Use

保留“新功能 / bugfix / refactor / 行为变更”这些触发条件，但补充：

- 对流程型功能、跨文件改动、工作流改动、技能行为改动，优先从 E2E/集成级测试起步
- 对无法自然形成 E2E 的任务，允许回退到小粒度起步

### 4. The Iron Law

保留：

> NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST

但新增默认解释：

> 默认情况下，这条 failing test 应该是复杂输入的 E2E 或集成级测试，而不是先拆到最小单元。

### 5. Red-Green-Refactor

主循环需要从单层循环改写成分层循环：

- RED：先写大粒度失败测试
- VERIFY RED：确认它因功能缺失或行为错误而失败
- GREEN：写最小实现让主流程跑通
- ESCALATE DOWN：仅当失败/异常难定位时，下钻补小测试
- RETURN UP：修复后回到大粒度测试验证
- REFACTOR：在主流程稳定后整理结构

### 6. Good Tests

“好测试”的定义要补充一条：

- 第一条测试应优先证明完整价值路径，而不是优先证明某个局部内部函数行为

### 7. Common Rationalizations

需要替换或追加新的反模式，重点打掉以下借口：

- “先从几个单测开始更稳妥”
- “E2E 太大了，不如先把内部函数都测完”
- “先把实现做出来，E2E 最后补”
- “大测试通过了，但还是把所有单测补齐比较标准”

并明确反驳：

- 默认先下钻会让代理过早陷入局部循环
- 大粒度通过后，默认不要求补齐全套小粒度测试
- 小粒度测试是定位工具，不是默认收尾动作

### 8. Verification Checklist

校验清单需要从“每个新函数/方法都有测试”转向更符合新流程的表述，例如：

- 第一条失败测试是否是大粒度测试（若任务适合）
- 第一条测试是否使用了相对复杂输入
- 是否真的先观察到大粒度测试失败
- 是否只有在失败/异常时才下钻到小粒度测试
- 若任务不适合 E2E，是否明确说明了例外原因
- 最终是否以大粒度测试通过作为主完成依据

“Every new function/method has a test” 这种要求不再适合作为统一硬规则。

## 与其他技能的衔接

### 1. `brainstorming`

无需改动其设计前置地位，但可在后续实现中检查其 spec/plan 话术是否默认为“小粒度 TDD”。若有，需要改为中性表述，不预设第一条测试一定是单测。

### 2. `subagent-driven-development`

该技能如果提到 TDD，应更新为：

- 执行子任务时遵循 `test-driven-development`
- 默认先写大粒度失败测试
- 仅在大粒度失败或异常时向下钻取小测试定位

### 3. `verification-before-completion`

该技能不必改变核心原则，但需与新 TDD 保持一致：

- 主完成依据优先看大粒度验收测试是否真实通过
- 不应把“是否补齐大量小测试”作为默认完成门槛

## 测试与回归设计

本次设计不仅改技能文案，还要同步改回归测试，避免技能更新后行为无保障。

### 1. 技能触发测试

保留 `tests/skill-triggering/prompts/test-driven-development.txt` 这一类触发测试，确保用户请求实现功能时仍然触发 TDD 技能。

### 2. 技能行为测试

新增或改造行为测试，验证代理在有 TDD 技能时会：

1. 先提出 E2E/集成级测试，而不是直接拆到多个单测
2. 第一条测试包含相对复杂输入，而不是最简单 happy path
3. 不会在没有失败信号时主动补全大量小粒度测试
4. 在大粒度失败时，能合理下钻到模块级测试定位问题
5. 在不适合 E2E 的任务上，能正确走例外路径

### 3. 显式技能请求测试

如果已有 `explicit-skill-requests` 测试体系，应补一个显式请求 TDD 的场景，验证用户要求使用 TDD 时，代理执行的是“大粒度优先”版本，而不是旧版“小粒度优先”版本。

### 4. 压力测试场景

需要用和 `writing-skills` 一致的方式验证以下高风险偏移：

- 代理在压力下是否重新退回“小单测先行”
- 代理是否会把“复杂输入 E2E”偷换成“非常简单的冒烟输入”
- 代理是否会在大粒度已通过后，仍习惯性补一堆无必要单测
- 代理是否会误把“我觉得不好定位”当成自由下钻许可，而不是基于失败/异常信号

## 风险

### 风险 1：代理把“大粒度优先”误读成“可以先实现再测”

这是最大风险，因此技能中必须反复强调：

- 仍然是 test-first
- 只是第一条失败测试的粒度变大
- 绝不允许“先写实现、后补 E2E”

### 风险 2：代理把“复杂输入”降级成简单 happy path

如果“复杂输入”的要求不够硬，代理可能形式上写 E2E，实际上仍只测一个最简单输入，失去本次优化价值。技能正文和测试都要明确卡住这一点。

### 风险 3：代理重新滑回“小粒度默认化”

如果“何时允许下钻”的条件不够明确，代理仍可能因为习惯而先补模块测试。需要用硬条件和反模式表格限制。

### 风险 4：某些任务其实更适合小粒度起步

这是真实存在的，因此例外路径必须保留。但例外应基于任务性质，而不是开发者偏好。

## 实施范围

### 必改

1. `skills/test-driven-development/SKILL.md`
2. 与 TDD 直接相关的行为测试/触发测试
3. 必要的邻接技能引用文案（如果其中明确写死“小粒度 TDD”）

### 可选调整

1. `README.md` 或面向用户的技能索引中对 TDD 的简述
2. 其他引用 TDD 的技能中的措辞一致性修正

## 验收标准

当本设计落地后，应满足以下标准：

1. 代理在实现常见功能任务时，默认先提出并编写复杂输入的 E2E/集成级失败测试。
2. 代理不会默认一开始就拆成多个局部单测。
3. 代理只有在大粒度失败、稳定性异常或性能异常时，才主动下钻到更小粒度测试。
4. 对天然不适合 E2E 的任务，代理能明确说明例外原因，并改用小粒度 test-first。
5. 大粒度测试已经通过时，代理默认不会再追补无必要的小粒度测试。
6. 相关测试能稳定区分“旧版小粒度优先行为”和“新版 E2E-first 行为”。

## 后续实现提示

实现阶段应优先做两件事：

1. 先补行为测试，证明当前技能仍然倾向小粒度起步（RED）
2. 再最小化重写 `test-driven-development` 技能正文，使其通过新的行为测试（GREEN）

这样可以让这次“流程文案重构”仍然遵守 `writing-skills` 所要求的技能级 TDD。
