# 实现验证准则

用于检查代码生成是否覆盖真实行为，而不是只保证单个函数能够编译。

## 通用顺序

1. 先运行格式化、静态检查和命中包测试，快速发现局部错误。
2. 存在自然业务链路时，验证该链路的最高自然层级。
3. 大粒度验证失败且定位不清时，再增加更小粒度测试。
4. 修复局部问题后回到真实链路验证，完成闭环。

测试需要环境初始化时，先搜索现有 `Init()` 或等价入口并复用。不要为了单次任务手写另一套数据库、缓存或配置初始化。

## HTTP 请求链路

当实现覆盖 `controller` 或 `router`，并且项目具备可运行的接口测试基础设施时：

- 验证 HTTP 方法、路径、绑定、鉴权或中间件、service 调用和响应契约。
- 同时检查失败输入与下游错误如何映射为响应。
- 不用每层一份单测代替请求到响应的链路验证。

若环境无法运行接口测试，至少运行相关包测试和编译，并明确未覆盖的外部依赖或运行环境。

## Service 与 Data 链路

仅修改 `service + data` 且没有 HTTP 入口时：

- 优先验证业务输入经过 service 编排后产生的查询、写入或缓存行为。
- 覆盖错误传播、空结果、边界条件，以及 N+1、事务或缓存一致性风险。
- 必须使用局部测试时，选择能复现本次行为或缺陷的最小边界。

## 定时任务链路

修改 `task` 时：

- 验证任务入口能够触发目标业务行为。
- 覆盖时间窗口、锁竞争、重复执行和失败返回语义中与本次改动有关的部分。
- 多实例语义无法在本地完整验证时，至少验证锁调用与失败分支，并说明残余风险。

## 无自然 E2E 的局部结构

纯 DTO、model 映射或序列化改动可以使用局部验证：

- DTO 验证 tag、校验规则、兼容输入和序列化结果。
- model 验证表名、字段映射、唯一键、软删除或缓存序列化。
- 不为不存在的 HTTP 链路虚构 E2E 测试。

## 失败信号

- 只说“建议补测试”，却没有实现或运行可用验证。
- 只验证单个 mock 调用，不覆盖本次真实行为。
- 未搜索项目初始化入口就自行拼装测试环境。
- 测试通过依赖跳过关键断言、吞掉错误或放宽生产逻辑。
- 扩大到未命中层，只为构造一个看似完整的测试链路。
