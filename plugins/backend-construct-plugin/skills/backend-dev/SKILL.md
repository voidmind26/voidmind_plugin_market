# Backend Dev

按当前项目的真实代码形态和插件内后端规范直接完成代码修改。除非用户只要求分析、诊断或计划，否则不要停在范围判断或实现建议。

## 核心原则

- 先读项目，再写代码。以仓库指令、相邻实现和现有测试为依据，不凭示例猜测项目结构。
- 只修改完成需求所需的最小分层，不因常见调用链自动扩面。
- 先保持项目一致性，再应用插件默认值；插件示例只用于补足项目中不存在的写法。
- 产出可运行代码，不留下 `TODO`、伪代码、占位函数或未接线实现。
- 直接在当前会话完成实现和验证，不创建固定目录的 plan，不要求选择执行模式，也不调用外部计划技能。

## 规范优先级

发生冲突时，按以下顺序处理：

1. 用户明确要求和当前目录适用的 `AGENTS.md`、`CLAUDE.md` 等仓库指令
2. 目标项目中同模块、同层的现有实现与测试约定
3. 本插件 `knowledge/` 和 `references/` 中的规则
4. 本插件 `examples/` 中的代码形态

若项目现状与插件示例不同，沿用项目现状；不要借业务修改迁移目录、框架或基础设施。

## 分层标签

在内部使用以下标签确定读取范围和实现边界，不要求把标签 JSON 暴露给用户：

- `dto`：请求、响应、参数字段和序列化结构。
- `data`：model、持久化实体、DAO/Repository、MySQL、Redis 和缓存对象。
- `service`：业务规则、业务编排、错误处理和跨数据源调用。
- `controller`：HTTP 参数绑定、service 调用和统一响应。
- `router`：路由注册和中间件接线。
- `task`：定时任务、周期任务、后台任务入口和调度接线。

只从用户请求和代码调用关系推断必要标签。“可能”“顺便”“看情况”等范围不直接纳入实现；只有候选层会实质影响接口、数据结构或行为且无法从代码确认时，才向用户澄清。

## 工作流

### 1. 建立项目证据

开始修改前：

1. 读取当前目录适用的仓库指令。
2. 查看工作区状态，识别并保留用户已有修改。
3. 定位目标入口、调用链、数据结构和测试。
4. 搜索至少一个同模块或同层的相邻实现，确认目录、命名、签名、错误处理、日志、依赖获取和测试初始化方式。
5. 记录仍会实质改变 API、表结构、兼容性或运行语义的不确定项；能从代码确定的事项不要追问用户。

### 2. 确定最小变更面

先读取 `../../knowledge/layering.md`，再按 `../../references/knowledge-map.md` 选择命中标签对应的资料。

- 先读命中层的 `../../knowledge/*.md`。
- 需要字段、签名、目录或禁忌项时，再读对应 `../../references/*.md`。
- 项目内缺少可复用代码形态时，才读对应 `../../examples/*.md`。
- 不加载未命中层的资料，不为未命中层创建“顺手完善”改动。

常见边界：

- 只改查询或缓存逻辑：通常为 `data`，有业务规则变化时再加入 `service`。
- 只改请求或响应字段：通常为 `dto`，绑定或响应流程受影响时再加入 `controller`。
- 新增完整 HTTP 接口：根据真实调用链覆盖 `dto + data + service + controller + router`；不需要持久化访问时不要强加 `data`。
- 新增定时任务：通常为 `task`，任务复用或新增业务逻辑时再加入 `service`。

### 3. 直接实现

- 复用项目现有包、公共组件、错误类型、日志库、依赖注入和初始化入口。
- 保持函数签名、命名、目录布局和同层代码风格一致。
- 让每层只承担自身职责，跨层数据和错误沿现有调用方向传递。
- 修改公共结构或接口时，搜索并同步必要调用方；不要用兼容性破坏换取局部编译通过。
- 新增行为时补充与风险相称的测试；修复缺陷时优先加入能复现缺陷的回归覆盖。
- 完成后检查 diff，移除调试代码、占位内容、无关格式化和超出需求的重构。

### 4. 验证

按风险从聚焦到完整执行验证：

1. 运行项目规定的格式化和静态检查。
2. 运行命中包或模块的聚焦测试。
3. 存在真实业务链路时，优先验证最高自然层级的集成或 E2E 行为。
4. 影响公共契约、共享组件或多层调用时，扩大到相关测试集。

涉及测试初始化时，先搜索项目已有初始化入口，优先复用框架测试包的 `Init()` 或等价方法。只有确认不存在统一入口时，才按相邻测试补齐初始化，不自行拼装另一套环境。

使用 `../../references/implementation-validation.md` 检查验证是否覆盖真实调用链。若某项验证因环境、权限或外部依赖无法执行，在结果中明确说明未验证部分和残余风险。

## 完成标准

- 用户要求的行为已经实现，而非只生成计划或建议。
- 修改范围与命中层一致，没有无依据扩展完整链路。
- 代码符合项目现有约定，并满足命中层规范。
- 必要调用方、注册入口和测试已同步。
- 已执行合理的格式化、测试或静态检查，并如实报告结果。

最终回复只需概括实现结果、关键边界和验证情况；除非用户要求，不输出内部标签载荷或冗长规范复述。
