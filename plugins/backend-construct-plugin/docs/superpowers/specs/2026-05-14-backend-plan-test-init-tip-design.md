# 后端开发插件测试初始化提示增强设计

## 背景

当前 `backend-construct-plugin` 已经通过 `write-plans-with-construct` 约束 plan 只覆盖命中层，并强调验证步骤优先采用更自然的大粒度验证边界。但在实际执行中，模型在为 Go 后端任务补测试或编写验证步骤时，容易因为初始化方式判断错误而反复循环，例如：

- 手写错误的测试环境初始化；
- 误用业务包初始化顺序；
- 没有先搜索项目内现成测试框架入口；
- 明明存在框架测试包统一 `Init()`，却从零拼装依赖。

这会让计划虽正确，执行却容易在测试初始化环节偏离项目既有约定。

## 目标

在后端 plan 阶段提前加入一条稳定的测试初始化提示，使模型在生成计划时明确：

1. 需要先在代码中搜索现有测试初始化方式；
2. 默认优先使用框架测试包下的 `Init()` 方法；
3. 只有在仓库中确认不存在统一 `Init()` 入口时，才改为遵循项目内其他现成初始化模式；
4. 避免因错误初始化导致反复补测、反复返工。

## 非目标

- 不在本次改动里新增新的分层标签；
- 不修改 `backend-dev` 的标签判定逻辑；
- 不把测试初始化沉淀成新的独立 knowledge 体系；
- 不强制所有项目都必须存在统一 `Init()` 实现；
- 不改变现有“验证优先大粒度、失败后再下钻”的测试策略。

## 现状观察

### 入口职责

- `skills/backend-dev/SKILL.md` 负责识别后端任务、收敛标签、路由到下游。
- `skills/write-plans-with-construct/SKILL.md` 负责基于已确认标签生成 plan，并定义验证步骤写法。

### 最合适的落点

测试初始化提示本质上属于“如何写验证步骤”的约束，而不是“如何识别层”的约束，因此最适合落在：

- `skills/write-plans-with-construct/SKILL.md` 的 Hard Rules / 验证步骤约束中。

如有需要，可在插件 README 中补一句能力说明，但核心行为应以 skill 约束为准。

## 可选方案

### 方案 A：只修改 `write-plans-with-construct` 的验证规则（推荐）

做法：

- 在 `Hard Rules` 中新增测试初始化规则；
- 在 `Plan Sections` 的“验证步骤”要求中补充搜索与默认初始化要求；
- 可选追加一个 pressure test / red flag，约束不要臆造初始化。

优点：

- 改动最小，直接作用于 plan 生成行为；
- 与当前 skill 职责一致，不污染标签识别层；
- 用户看到的 plan 会自然带出这条 tips；
- 后续维护集中在一个地方。

缺点：

- 该约束主要影响 plan 文本，对更上游路由层没有显式感知。

### 方案 B：同时修改 `backend-dev` 与 `write-plans-with-construct`

做法：

- 在 `backend-dev` 中为下游载荷增加“测试初始化注意事项”；
- 在 `write-plans-with-construct` 中消费该注意事项并展开。

优点：

- 从路由到 plan 都能显式携带这类上下文。

缺点：

- 为一个稳定通用规则引入新的载荷复杂度，收益不高；
- 会让 `backend-dev` 承担本不属于分层识别的测试策略细节。

### 方案 C：新增独立 reference/knowledge 文档，再由 plan skill 引用

做法：

- 新增类似 `references/testing-conventions.md`；
- 在 `knowledge-map.md` 中给相关标签接入；
- `write-plans-with-construct` 在需要时读取。

优点：

- 规则文档化更完整，后续可扩展更多测试约定。

缺点：

- 对当前这个“小 tips”来说偏重；
- 会扩大插件知识面和维护成本；
- 目前缺少足够多的测试规则内容来支撑独立文档。

## 推荐方案

采用 **方案 A：只修改 `write-plans-with-construct`**。

原因：

- 用户诉求是“在 plan 中明确告知模型”；
- 现有职责边界下，plan 生成 skill 就是正确落点；
- 这是一条通用执行约束，不需要变成新的上游输入字段；
- 先用最小改动验证效果，后续若测试规则继续增长，再考虑独立 reference。

## 设计细节

### 1. 新增测试初始化硬规则

在 `skills/write-plans-with-construct/SKILL.md` 的 `Hard Rules` 中新增约束，表达为：

- 当计划包含测试、验证、补测、E2E、集成验证、单测等动作时，必须先要求模型在代码中搜索现有测试初始化入口；
- 默认优先使用框架测试包下的 `Init()` 方法作为测试环境初始化入口；
- 若搜索后确认不存在统一 `Init()`，再遵循仓库内现成测试入口或已有测试模式；
- 禁止在未搜索现有模式前，直接规划手写初始化。

### 2. 强化验证步骤写法

在 `Plan Sections` 对“验证步骤”的要求里补一条显式文案，要求计划写出类似含义：

- “先搜索项目内测试初始化方式，默认复用框架测试包的 `Init()`；若不存在，再按仓库现有测试样式补齐。”

这会让计划输出中稳定出现该 tips，而不是只停留在 skill 内部规则。

### 3. 补充失败信号

在 pressure tests / red flags 中补充以下失败信号之一即可：

- “直接手写测试初始化，不先搜索现有 `Init()` 入口”；
- “假设测试环境需要自行拼装数据库、缓存、配置初始化”；
- “没有验证仓库内是否已有统一测试框架入口”。

这样能让未来继续迭代 skill 时，不容易把该约束回退掉。

## 建议文案方向

建议在 skill 中使用偏稳定、可执行的措辞，而不是项目特定硬编码。推荐表达：

> 涉及测试或验证实现时，先在代码中搜索现有测试初始化方式；默认优先复用框架测试包下的 `Init()` 入口。只有在确认仓库不存在统一 `Init()` 时，才改为遵循现有测试样式补齐初始化，避免自行拼装错误环境。

这样既体现“默认 `Init()` 优先”，又保留对不同仓库现状的兼容性。

## 影响范围

### 直接影响

- `skills/write-plans-with-construct/SKILL.md`

### 可选同步

- `README.md` 可补一条说明：该插件在验证步骤中会显式约束测试初始化优先复用项目现有入口。

但 README 同步不是必须项，除非你希望对使用者公开这项行为。

## 测试与验收

本次是 skill 文案增强，验收重点不是代码编译，而是规则是否稳定反映到 plan 输出。

建议验收方式：

1. 用一个包含测试/补测/E2E/集成验证需求的后端任务触发 `backend-dev -> write-plans-with-construct`；
2. 检查生成的 plan 是否明确要求先搜索测试初始化方式；
3. 检查 plan 是否默认指向框架测试包 `Init()`；
4. 检查 plan 是否避免直接要求“手写初始化”；
5. 检查原有大粒度验证优先规则未被破坏。

## 风险与控制

### 风险 1：文案过于绝对，误伤没有统一 `Init()` 的仓库

控制：

- 用“默认优先”“先搜索，确认不存在后再退回现有样式”的表述，不把 `Init()` 写成强制唯一方案。

### 风险 2：规则只写在 Hard Rules，最终输出 plan 不可见

控制：

- 同时在“验证步骤”要求中加入显式输出约束，而不是只写内部原则。

### 风险 3：未来改 skill 时该提示被无意删除

控制：

- 在 red flags / pressure tests 中补一条失败信号，提升回归可见性。

## 实施边界

本次实现应保持最小改动：

- 必改：`skills/write-plans-with-construct/SKILL.md`
- 可不改：`skills/backend-dev/SKILL.md`
- 可选：`README.md`

不新增额外知识文档，不调整标签体系，不引入新 JSON 字段。
