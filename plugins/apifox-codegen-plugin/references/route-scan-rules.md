# 路由扫描规则

## 1. 识别范围

只接管 Go Web 代码中的接口扫描任务，目标是从 router -> controller -> service -> dto 链路提取接口信息。

优先识别以下组织形态：

- router 或 route 文件中注册 method + path + handler
- controller 中负责参数绑定、调用 service、组织返回
- service 中承载业务语义和数据编排
- dto 中定义请求/响应结构、json 标签、字段类型

若项目明显不具备这类链路，例如只有前端路由、只有 SDK 封装、没有 HTTP handler 入口，则保守退出，不假装完成扫描。

## 2. 前缀 / 全部接口规则

### 默认规则

默认要求用户提供路由前缀，只扫描该前缀命中的接口。

示例：

- `/user`
- `/order`
- `/admin/report`

前缀的作用是收缩扫描面，避免把整仓接口一次性卷入。

### 全部接口规则

只有当用户明确确认“全部接口”时，才允许全量扫描。

执行前先明确说明：

- 这是全量扫描，不是局部补文档
- 扫描量可能较大
- 结果中仍需逐条按链路取证，不能靠目录名批量猜测

未拿到明确确认前，不进入全量扫描。

## 3. 各层提供的信息

### router 提供什么

router 负责提供接口入口事实：

- HTTP method
- 完整挂载路径 `fullRoute`
- handler / controller 入口函数
- 路由分组、公共前缀、中间件线索

router 是范围筛选起点，不负责完整请求/响应定义。

### controller 提供什么

controller 负责提供接口外观信息：

- 接口名或注释说明
- 参数绑定入口
- 请求 DTO 引用
- 响应返回入口
- 成功 / 失败分支的初步语义

controller 是“这个接口对外长什么样”的第一手来源。

### service 提供什么

service 负责提供业务语义：

- 核心业务动作
- 状态分支与错误语义
- 聚合逻辑、查询组合、流程顺序
- 哪些响应字段是业务结果，哪些只是包装层

service 常用于补足接口说明草案，以及区分真实业务返回与通用包装。

### dto 提供什么

dto 负责提供结构化定义：

- 请求结构
- 响应结构
- 字段类型
- json 标签
- 可推断的字段说明与示例线索

dto 是 schema 的主要依据。若 dto 缺失，再回到 controller 返回结构或通用响应包装做保守推断。

## 4. 提取目标

每个接口至少提取以下信息：

- `method`
- `apiPath`
- 接口名
- 请求结构
- 响应结构
- 接口说明草案

同时允许保留证据字段，便于回溯：

- `fullRoute`
- handler 名
- controller / service / dto 来源路径

注意：`fullRoute` 只用于扫描和取证；写入 Apifox 时，`path` 只保留 `apiPath`。

## 5. 保守降级规则

没有完整注释时，允许依据代码约定推断，但必须保守。

### 允许推断的内容

可以根据以下线索整理草案：

- handler / service / dto 命名
- 请求参数字段名
- 返回包装结构
- 常见错误码或状态字段
- 已存在的同组接口命名风格

### 禁止伪造的内容

不要伪造以下无法合理确定的信息：

- 未在代码中出现的业务规则
- 无法确认的枚举含义
- 无法确认的字段默认值
- 无法确认的嵌套响应结构
- 无法确认的示例数据语义

### 降级策略

遇到信息不足时，按以下顺序降级：

1. 先保留最小确定事实：method、apiPath、handler、已知 DTO 字段。
2. 说明哪些描述来自代码推断，而不是注释原文。
3. 无法确定的字段留空、标记待确认，或仅保留顶层结构。
4. 不为“看起来完整”而补写未经证实的信息。

## 6. 结果质量要求

扫描结果应满足：

- 范围明确：前缀扫描或已确认全量扫描
- 链路完整：尽量经过 router -> controller -> service -> dto 取证
- 说明可追溯：知道每项结论来自哪一层
- 推断可解释：能区分代码事实与合理推断
- 降级可接受：信息不足时保留最小可用结果，而不是伪造完整文档
